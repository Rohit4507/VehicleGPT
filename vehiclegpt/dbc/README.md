# CAN databases

Two DBC files, with deliberately different provenance. **Do not conflate them.**

| File | Source | Licence | What it is |
|---|---|---|---|
| `tesla_can.dbc` | [commaai/opendbc](https://github.com/commaai/opendbc) | **MIT** | A **real production DBC** for Tesla Model 3/Y. Vehicle dynamics, pedals, steering, gear, ADAS state, ambient temperature. 44 messages, 331 signals. Vendored unmodified |
| `vehiclegpt_vendor_ext.dbc` | **Written by this project** | MIT | A **synthetic vendor extension** covering the HV battery pack, HVAC and energy. 3 messages, frame IDs `0x6A0`–`0x6A2` |

## Why two files

`tesla_can.dbc` gives us genuine OEM frame layouts, bit positions, scaling and
byte order. Encoding physical values into it with `cantools` and decoding them
back is byte-identical to what a real vehicle does. That is the entire credibility
argument for the CAN demo — see `docs/04-architecture.md` §5.

But the real DBC has **no HV battery pack signals**. Tesla pack CAN is
proprietary and is not published, for good reason. Neither is any other OEM's.
So "battery overheating" cannot come from a real DBC, and no amount of searching
fixes that.

The vendor extension therefore models the pack, HVAC and energy signals
ourselves — which is exactly what an OEM does when it adds vendor properties to
the vehicle bus (the same pattern as `VehiclePropertyGroup:VENDOR` in Android
Automotive's VHAL, see `docs/02-research-findings.md` §5).

Frame IDs `0x6A0`–`0x6A2` are chosen to sit outside the range used by
`tesla_can.dbc`, so the two databases can be loaded onto the same bus without
collision. Verified by `tests/test_dbc.py`.

## What is real and what is not

| Aspect | Status |
|---|---|
| Frame layout, bit packing, scaling, byte order of `tesla_can.dbc` | **Real** — unmodified OEM database |
| Encode → bus → decode round-trip | **Real** — actual `cantools` + `python-can` code path |
| Physical values flowing through those frames | **Synthetic** — generated by `sim/`, not recorded |
| `vehiclegpt_vendor_ext.dbc` layout | **Synthetic**, but physically plausible (pack voltages, thermal coefficients, HVAC draw ranges) |
| Fault sequences (battery overheat, ADAS disengagement) | **Synthetic, injected, with known ground truth** |

The honest one-liner: *"the bus is real, the DBC is real, the frames are real —
the driving is simulated."*

## Regenerating the vendor DBC

It is generated from a `cantools` `Database` object rather than hand-written, so
the encoding is valid by construction:

```bash
python3 tools/make_vendor_dbc.py
```

Hand-editing the `.dbc` is fine for small changes but you lose the round-trip
guarantee; re-run the generator instead.
