# 10 — Tier C latency: what the 8 seconds actually is, and the four ways out

**Status of this document.** Every number below is `[D]` — arithmetic over the
`[M]` anchors in [doc 06 §11](06-hardware-feasibility.md#11-claims-ledger) — unless
explicitly tagged otherwise. No figure here is a measurement of VehicleGPT, and
none is a benchmark of any model on Tier C hardware. The one `[M]` input is a
Raspberry Pi 5 measurement of somebody else's model, scaled by a PassMark ratio.

---

## 10.1 The concern, stated fairly

> On a Cortex-A53 (Tier C), P1 with Qwen3-0.6B takes ~8 s. That violates the
> 2-second constraint outright. If the judges ask how Tier C meets it on P1,
> the answer rests entirely on P0.

That is directionally correct and it is the sharpest risk in the project. One
detail needs correcting before it drives a decision, because it changes which
lever to pull.

**8,073 ms is the P1 *total*, not the prefill time.** The split matters:

| Component | Time | Share of total | Evidence |
|---|---|---|---|
| Prefill (50 re-prefilled tokens of 140) | 3,030 ms | 37.5 % | `[D]` |
| Decode (28 output tokens) | 4,912 ms | 60.9 % | `[D]` |
| Pipeline (parse, SQL, assemble, no model) | 130 ms | 1.6 % | `[D]` |
| **Total** | **8,073 ms** | | `[D]` |

Generated by `make model`, section *"Where the Tier C time goes"*.

Decode is the dominant cost, not prefill. The instinct on hearing "8 seconds" is
to shorten the prompt. That instinct is wrong here.

---

## 10.2 Two necessary conditions

Ignoring every other part of the system, a candidate model must clear **both**
of these on Tier C to meet the target on P1:

| Condition | Threshold | Qwen3-0.6B (projected) | SmolLM2-135M (projected) |
|---|---|---|---|
| Prefill, even if decode were free | ≥ 26.7 tok/s | 16.5 ✗ | 76.0 ✓ |
| Decode, even if prefill were free | ≥ 15.0 tok/s | 5.7 ✗ | 26.2 ✓ |

Qwen3-0.6B misses the decode threshold by 2.6×. This is why no amount of
prompt engineering, KV-cache tuning or batching rescues it: you cannot
precompute your way out of a decode-rate deficit when decode is 61 % of the
budget.

The thresholds depend only on the path shape and the target, so they are valid
**before** any model has been benchmarked. `tools/phase0/bakeoff.py
--required-only` emits them, and a test asserts they agree with the feasibility
model — both derive from `tools/paths.py`, so if they drift, one of them is
wrong.

---

## 10.3 Why trimming the prompt is not the answer

Suppose prefill became instantaneous. P1 on Tier C would still cost
130 + 4,912 = 5,042 ms `[D]` — 2.5× over budget. Conversely, if decode were
instantaneous, prefill alone is 3,030 ms, still over.

Both halves fail independently. A fix has to address decode rate, which means
fewer parameters or better hardware — or not decoding at all.

---

## 10.4 The four options

| # | Option | P1 on Tier C | Quality floor | Cost | Verdict |
|---|---|---|---|---|---|
| A | SmolLM2-135M for every query | 1,857 ms `[D]` — 93 % of budget | Unknown; 135 M is small for causal explanation | Low | **Fragile.** 7 % margin over an extrapolation-of-an-extrapolation |
| B | Precomputed explanation cards, no decode at query time | 110 ms `[D]` (P0 path) | High — the explanation was written with full context | Medium: card generation is offline | **Recommended primary** |
| C | 0.6B model as an explicit "deep analysis" mode | 8,073 ms `[D]` | Best | Already planned | **Keep, relabel** — not the default |
| D | Run Tier C queries on Tier B hardware | 1,579 ms `[D]` | Best | Hardware cost | **Not a Tier C answer**; it is an argument for a different tier |

### Why A is fragile even though it passes on paper

1,857 ms is 93 % of a 2,000 ms budget, and every input to that figure is
`[D]`. A 20 % error in the PassMark scaling — entirely plausible, since it
compares a Xeon-class ratio across a different microarchitecture — puts it at
2,230 ms. An option whose pass depends on the accuracy of an extrapolation is
not a passing option; it is a coin flip with a bibliography.

There is also a quality question that no latency table can answer: a 135 M model
answering *"why has my range reduced?"* is being asked to reason over evidence
blocks and resist inventing numbers. That is hard for a 7 B model. The accuracy
half of the bake-off exists precisely to test this, and it is the half most
likely to fail.

### Why B is the strongest option

Doc 06 already models an L3 tier of **explanation cards** — 180 cards/day,
320 bytes each. A card is written *at ingest time*, when there is no latency
budget and the full context is available. At query time the system retrieves the
matching card and fills a template. No decode, so no decode-rate problem.

This converts an unsolvable latency constraint into an offline computation. It
also produces better answers than a 135 M model would, because the card was
written by a model with time and context to spare.

The objection is fair: the case study asks for an on-device SLM/LLM. B does not
remove the model — it moves it off the critical path, and keeps option C
available for the questions a card cannot cover.

## 10.5 Routing by query class

The five example queries from the brief do not all need the same machinery.
Classifying them is the actual resolution of R1/R2:

| Query from the brief | What it needs | Path | Tier C latency |
|---|---|---|---|
| "Show all ADAS disengagement events from yesterday." | Filter + enumerate | P0 | 110 ms `[D]` |
| "When did fuel efficiency show the largest drop?" | Aggregation + argmax | P0 | 110 ms `[D]` |
| "Compare energy consumption between city and highway." | Two aggregates + ratio | P0 | 110 ms `[D]` |
| "What happened before the battery overheating warning?" | Event-sequence retrieval + template | P0 (card) | 110 ms `[D]` |
| "Why has my driving range reduced?" | Causal ranking over factors | P0 card, escalating to P1/P3 | 110 ms `[D]`, or 8,073 ms `[D]` if escalated |

Four of the five are answerable without decoding a token. The fifth escalates
only when the user explicitly asks for free-form analysis — at which point the
UI has already told them it will take a moment.

That is not a workaround dressed up as a design; it is how production automotive
assistants are built, and it is defensible on its own merits. It also means the
honest Tier C claim is narrower and stronger than the current one:

> On Tier C, every query class in the brief is answered within the target
> `[D]`, with the LLM reserved for explicit deep-analysis requests that are
> labelled as such before they start.

## 10.6 What the bake-off decides, and what it cannot

`tools/phase0/bakeoff.py` replaces the 135 M projection with a measurement. It
is honest about its own limits:

**It can decide:** whether SmolLM2-135M actually decodes at ≥ 15 tok/s and
prefills at ≥ 26.7 tok/s *on a named machine*; whether its answers survive a
grounded-fact check; and how it compares with Qwen2.5-0.5B, SmolLM2-360M and
Qwen3-0.6B, on the same paths, in one command.

**It cannot decide Tier C,** unless it is run on Tier C hardware. A run on the
RTX 3050 laptop measures the laptop. The harness stamps every result with the
machine it ran on and prints a warning when that machine is not ARM, because
that distinction is exactly the one this project has already been burned by.

The harness is tested against a mock backend (`--backend mock`), so the parsing,
scoring and verdict logic are exercised before anyone points it at real weights.
A harness that has never produced a number is not evidence that the harness
works.

### Running it

```bash
# what must a model be able to do? (no model needed)
python3 tools/phase0/bakeoff.py --required-only

# real measurements, on whatever machine you are on
python3 tools/phase0/bakeoff.py --models ~/models/SmolLM2-135M*.gguf \
                                --models ~/models/Qwen3-0.6B*.gguf \
                                --eval --json > bakeoff.json
```

Requires `llama-bench` and `llama-cli` from [llama.cpp](https://github.com/ggml-org/llama.cpp).
Weights must come from Hugging Face, which the development sandbox cannot
reach — so this bake-off has **not** been run, and this document does not
pretend otherwise.

## 10.7 What would change this recommendation

- **Bake-off shows 135 M at ≥ 25 tok/s decode on ARM with acceptable accuracy.**
  Option A becomes viable as the default for causal questions, and B becomes an
  optimisation rather than a necessity.
- **Dreamer/other hardware lands in the Tier C envelope.** Option D collapses
  into B being unnecessary.
- **Card coverage turns out poor.** If the offline generator cannot anticipate
  the question shapes, escalation rates rise and the 8 s path becomes common.
  Phase 2 must measure the escalation rate, not assume it.

Until one of those happens, Tier C does not meet the 2-second target on P1, P2
or P3 `[D]`, and this repository should keep saying so.
